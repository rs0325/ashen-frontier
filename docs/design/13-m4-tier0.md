# M4: Tier 0（確定）

## M3の確定範囲（2026-11-25）

M3 Q1〜Q8は全て推奨案で承認済み。[14](14-m3-climate-survival.md)を詳細正本とする。M3はA「気候とM4接続」、B「生理・感染」、C「序盤動物」に分割し、Aのみで全体完了としない。

高度な星空/惑星描画・建築被害・精密観測器・重症医療/ワクチン・家畜治療/細胞採取等の移管先は[15](15-phase1-followups.md)。従来の確定目標は維持し、M3の実装時期についてはこの決定を優先する。

既存貯留の蒸発・減水・水位の共有契約は未決定。[#136](https://github.com/rs0325/ashen-frontier/issues/136)と水量正本の[#122](https://github.com/rs0325/ashen-frontier/issues/122)/実配置の[#123](https://github.com/rs0325/ashen-frontier/issues/123)で調整する。非負補給APIへの負量入力や残量の二重保存は行わない。


[08-phase1.md](08-phase1.md)のM4を対象とする。2026-11-24、Q1〜Q8をすべて推奨内容で承認。設計正本はdocs/design/13-m4-tier0.md。M2の保全区の具体配置は未決定であり別途承認を要する。

## 目的

石器、火、有限水の処理、栽培、調理・保存によって安定した生活を成立させる。初期配布・遺物は立ち上げを助け、日常消耗品は自製・増殖で維持する。

## 主な製法【確定】

加工は台石・炉・槽・棚で行う。クラフトグリッドは単純な組立だけ。最初の台石・礫器・紐・火起こし具・播種を研究で自己ロックしない。

| 工程 | 操作 | 条件と結果 |
|---|---|---|
| 打製 | 台石へ材料を入れ、打撃具で加工開始 | 石材1 kg→礫器0.7 kg＋0.1 kg剥片3個、礫器→両面刃0.5 kg＋剥片2個。10/20実秒。工具は保持して摩耗 |
| 紐・柄・布 | 台石で撚り/切削、枠で編む | 繊維1 kg→紐0.1 kg×9と損失0.1 kg。枝1 kg→柄0.8 kg＋損失0.2 kg。10〜30実秒 |
| 柄の取付け | 所持品2×2組立 | 両面刃0.5＋柄0.8＋紐0.1 kg。斧/手斧を作る。一般採鉱用工具にはしない |
| 火起こし | 弓錐で炉を30実秒操作 | 火口・乾燥薪・覆いが必要、確率失敗なし。離れると停止、成功時に火口消費 |
| 土器 | 台石成形→棚乾燥→炉焼成 | 粘土2＋砂0.5＋水0.5 kg。成形10実秒、乾燥1ゲーム日、焼成973〜1123 Kで120実秒。完成土鍋は4 kg容量・非スタック |
| 沈殿/ろ過 | 静置容器→布砂砂利槽 | 濁水4→生水3.6＋保持水0.4 kg。静置半ゲーム日、ろ過30実秒。布10バッチで交換 |
| 煮沸 | 炉上土鍋 | 生水4→清浄水3.8＋蒸発0.2 kg。局所沸点到達後60実秒、高地約2000 m超は180実秒。冷却保管。化学汚染は除けない |
| 手動揚水 | 井戸到達を確認し手動操作 | 10実秒で最大1 kg。現在量から減算、元の水質を保持。浅井戸吸上げのSI m/気圧を検査 |
| 太陽熱蒸留 | 原水投入後の日射積算 | 非揮発性汚染を代表する汚染水のみ、4 kgから上限2 kg、晴天2 kg/m²/ゲーム日目安。日照・冷却面が必要 |
| 燃料蒸留 | 陶製蒸発器と空冷管を炉で加熱 | 同4→2 kg、残水2 kg。燃料入力3 kW、熱利用20%。20℃から約5.85 MJ有効熱、約9740実秒、気乾薪約1.83 kg |
| 雨水回収 | 上空が開いた集水面と容器 | 質量＝面積m²×降水mm×0.7 kg/(m²·mm)。通常raw、汚染降雨はcontaminated。凍結時停止 |
| 栽培 | 掘り棒・種使用・手灌水・収穫 | 環境適合区間のみ成長、乾燥は停止、未熟破壊は種返却。採種モードを表示 |
| 菌床 | 基質加熱→冷却→接種 | 清浄残渣・水・菌種を消費し、3ゲーム日で子実体と継代用菌種。基質は交換 |
| 調理 | 台石で手挽き→炉で煮炊き | 主食/葉菜/菌は標準120実秒、豆は浸漬半ゲーム日＋300実秒。清浄水を消費、汚染/腐敗を無条件に初期化しない |
| 保存 | 下処理後の炉脇棚 | 323〜333 K、湿度適合、1ゲーム日。乾物の腐敗閾値10倍、永久保存なし |
| 肥沃化・薪 | 槽熟成/萌芽更新/棚乾燥 | 堆肥4日、薪乾燥1日、木の再生6日。残渣を堆肥/菌床/燃料で二重計上しない |

質量は材料データ/既存CONTENT_MASSを使う。固体の部分消費基盤を増設せず、新規品の単位質量と個数、明示損失で収支を合わせる。水の部分移送はkg残量を保存し、mBとの換算は密度に基づく。

汚染水蒸留→清浄水は設計03を引き継ぐが、現実の揮発性汚染を除去できない制限を明記する。原水が非揮発性汚染の代表であるという簡略化はQ3で確定する。有毒水/汚染海水は拒否。濃縮残水は既存品質を保つ飲用不可・再投入不可のバッチ状態として保持し、新規第9水質を作らない。持出し・再配置でも残水制限を維持する。安全廃棄操作に抽象化し、廃棄でsourceを作らない。

低温土器の漏水省略、数十秒の石器加工、短い焼成/加熱時間はゲーム簡略化。燃料と水の熱収支は別に保ち、機械/燃焼の実秒と長期のゲーム秒を混ぜない。

## 作物・土壌・栄養【確定】

16面を大麦8・大豆4・葉菜4とし、周期4/4/2ゲーム日、1面収量0.4/0.2/0.25 kg。麦1面0.025 kg以上、大豆は1/8を再播種へ取り分ける。葉菜は1面を採種へ切替。菌・亜麻・薪の区画は別枠。1ブロックは集約栽培区、作期と水量も圧縮する。

標準食の例は麦乾燥換算0.5＋大豆0.2＋葉菜0.25 kg/日。仮受入値は10 MJ、たんぱく質0.06 kg、脂質0.04 kg、水分3 kg/人日とM3簡略ビタミン区分の充足。医学的な基準値ではない。固定栄養データと加工後の値は同じ単位でM3へ渡す。

全微量栄養素（B12等）の長期充足は植物中心の標準食では保証しない。M3第1期のビタミン類は簡略区分、厳密な微量栄養管理は後続提とする。土のN/P/K収支と亜麻精練も集約するゲーム簡略化としてQ2/Q7で承認済み。現実の完全栄養食・閉鎖生態系の再現とは説明しない。

土の質は堆肥で改善できるが汚染は減らさない。清浄段階でも食用の適合保証ではない。M3との適合未確認床では食用栽培を開始させず、安全床への交換/移動を案内する。土段階を食品の数値汚染へ変換しない。汚染作物・移行係数と酸中和等は後続提。

## 水量の所有・加工確定・容器（2026-11-24追加確定）

- 容器/水源から槽へ1操作で移した後の水量は設備が所有する。世界の水源の現在量・採水/移送とその原子性は#55が所有する。
- 加工は開始時に槽の必要量を確認する。予約は行わず、サーバーで全出力を確定する時点で槽からの消費と出力を一度に確定する。
- 取消・出力満杯・保存再開では未消費水を槽へ残す。水源へ戻さず、複製/消失させない。
- 容器は同じIDでCONTENT_MASSと水質を保持し、0 kgは空容器。部分消費では品質を維持する。異品質の混合は規則がないため拒否する。
- #106は設備槽と加工を実装し、#55より先に必要な容器↔槽の移し替えだけは先行実装できる。世界の水源・帯水層・その量保存には触れない。

## 既存実装の再利用と差分【確定】

- CommonRecipeの入力/複数出力・RecipeConditions・RecipeTypeRegistryを使用する。matchesは実行条件を強制せず、assembleは先頭出力だけのため、設備が全条件・全出力・消費/返却をサーバーで一度だけ確定する。
- 品質一致には導入済みNeoForgeのDataComponentIngredientを使う。水kg・入力役割・消費/損失・属性継承は同レシピIDの限定的加工データで補足する。独自レシピ検索器/実行言語を作らない。参照不正はreloadで拒否、加工中レシピ変更は停止して未加工入力を返す。
- 型ごとの時間系表示を最小追加する。既存型の実秒の意味は維持。作物/堆肥のデータは生育責務に置く。
- MaterialData/FuelData、ItemPropertiesの温度・摩耗・汚染・腐敗・丸め、GameTimeを使う。既存の数値汚染・soil_contamination・容器保存形式を変更しない。
- 新しいデータは固定nutrition、必要な可変栄養、crop_species、設備の加工/残水状態。不要な将来遺伝子フィールドを置かない。
- ResearchManager.registerConditionType/report/reportKnowledge、チーム保存、TerminalAttachments/Screenを使用する。配布履歴SavedDataを端末や研究に置かない。
- 機能Modがないcore登録遺物は静的回収物のまま。旧設備のID変更で修復を表さない。

## 進行・詰み防止【確定】

- 台石・打撃石・礫器・紐から再開可能。適性工具なしに幹・鉱石・遺物を破壊して迂回しない。
- 初期資料は再閲覧、初期必須品はUUID配布。死亡や移籍で再配布しない。
- 全種/菌喪失の回復は、母株/菌種を残す固定の生きた繁殖保全区を追加する。2日以上の再生と区画水/栄養予算を持ち、母株全破壊の保護範囲を別途承認。座標・外観はM2提案で決める。無から種を配る機構は作らない。
- 水は6 kg/人日を基礎予算、6日無雨で36 kg/人以上の基礎貯蔵。菌/繊維/薪畑の追加用水を上乗せ。太陽熱・燃料蒸留を各プレイヤーの毎日必須にしない。
- 有限地下水は正しく枯れる。承認気候の降水/涵養がある条件で長期収支を閉じ、任意長の永久干ばつ保証はしない。
- 満杯出力は設備内保持、破壊/再設置でも現在量と加工開始時の入力を保存。採水・研究・完成はサーバーで一度だけ。
- 管理者rescueは不具合用。通常の種増殖/水供給の代用にしない。

## #106の共有APIと保存形式（2026-11-24）

### モジュールと所有者

`ProcessingStation`は設備の加工状態であり、Block/BlockEntity/道具の本体ではない。槽・入力・出力・工具・進捗を同じ設備の保存へ含める。設備は実際に移した物だけを`setInput`/`setTool`へ渡す。インベントリ間の移動と外部ケイパビリティは提供しない。

primitiveとagricultureはcoreを参照し、agricultureからprimitiveへのソース依存を追加する。climate未実装の基盤段階ではローダー上のclimate依存はoptionalとし、気象が必要な加工は`EnvironmentSample`未提供なら停止する。機能上の気象依存は維持し、代替の値は持たない。

自然配置する植物・収穫物の実体登録は#111でcoreへ追加する。#106は栄養/種別の成分と加工型を登録し、設備や植物の仮の本体を先取りしない。

### 加工データ

`CommonRecipe`の同じJSON内に任意の`processing`を持つ。既存RecipeManager・serializer・同期を使い、別のレシピ辞書/再読込機構は追加しない。省略時は既存どおり材料各1個。型の時計は`TimeBasis`で指定し、従来の型は実秒のまま。

| フィールド | 意味 |
|---|---|
| inputs | 0始まりのIngredient番号・count・保持するかretained。実スロット順ではない |
| water | quality（水質ID）、mass_kg（確定時に槽から引く正のkg） |
| loss_kg | 工程損失kg。レシピ制作者が入力と全出力の物質収支を確認する |
| tool_wear | catalyst工具の摩耗増分。既存の摩耗刻みへ切り上げ、工具は保持し、Wear上限超過は拒否 |
| inheritance | 原料番号と出力番号。腐敗・数値汚染・放射能・個別栄養を保持。複数原料の混合モデルは導入せず、同一出力への重複指定は拒否 |
| requires_environment | 気象入力の要否。温度/圧力条件またはGAME時計の型も未接続では停止 |

番号の範囲/重複、個数、水質参照/正量を読み込み時に検査する。成分付き入力と触媒の部分一致はNeoForgeの`DataComponentIngredient.of`を使う。

`matches`は材料照合、`assemble`は先頭出力のプレビューであり加工確定ではない。`start`は現在のRecipeManagerから材料・設備・研究・水量を確認し、予約/事前消費しない。`advance`は単調なgameTime差を型の時計へ換算し、設備が区間に供給した実エネルギーJを受ける。環境条件外の区間は進めない。

`finish`は現在のレシピ定義・入力・工具・研究・条件・水量と全出力の空きを再検査し、入力消費・槽消費・工具摩耗・複数出力を一操作で確定する。満杯は状態保持、取消は入力/槽を変更しない。別プレイヤーによる再開始/二重確定は成功しない。変更APIはサーバースレッド専用。

`save`/`load`で設備内の全状態を保存・復元する。`load(tag, registries)`はBlockEntityの`loadAdditional`が受け取る`HolderLookup.Provider`を使い、プレイヤーやLevelを必要としない。復元後最初の`advance`で時計を合わせ、未ロード時間は加工へ加えない。現在のレシピ/研究を再検査し、reloadで定義が削除/変更されたら加工だけ停止して未消費入力/水を残す。完了後保存から再生成しない。未リリースの新規保存形式なので移行は追加しない。

材料照合は空きを除いた材料数を検査し、返す番号は設備の元のスロット番号とする。消費・属性継承もその番号を使う。研究とレシピの両方がロードされた起動時・reload完了時に、`conditions.research`を有効な研究定義と照合する。存在しない研究（前提不正で無効な研究を含む）への参照はレシピID・研究IDをログに示し、そのレシピをRecipeManagerから除外して同期する。

### 槽・容器

`WaterTank.Contents`は容量kg・現在量kg・水質IDを保存する。`fill`は#55等が既に確保した水を受ける入口で、水源を減算しない。先行実装する`fromContainer`/`toContainer`は実移送kgを返す。容器容量は設備/UIが登録仕様から渡し、複数個スタックは事前に1個へ分割する。異品質混合・不正量・容量超過を拒否する。空容器は残していた品質によらず再充填できる。

空槽は品質なし、空容器は同ID・0 kg。部分移送で品質は変えず、`RelicProperties.container`も0 kgを作成できる。世界のsource・帯水層・その保存は追加しない。

水量の分解能は1 mg（0.000001 kg）とする。`WaterMass`を唯一の単位変換境界とし、槽の量・容量と、容器↔槽の加減算・比較・移送はすべてlongのmgで行う。許容差による比較はしない。槽が0 mgになったら品質を消す。既存`CONTENT_MASS`と槽のkgのdouble保存形式は維持し、保存値を読み込む時に最寄りのmgへ丸める（ちょうど半分は切上げ）。表示・保存・既存kg APIの境界でだけkgへ変換する。

レシピの加工水量と水入り出力の量も同じ格子を使い、格子に乗らない制作値は読み込みエラーとする。保存値の丸めと制作データの検査を区別する。doubleのkg保存で1 mgを区別して往復できる範囲として、水量・容量の数値上限を10億kgとする。0 mgへ丸まる移送指定や容量は不正指定とする。毎tick処理は増やさず、変換は操作・読込・保存時、量の演算は定数時間の整数演算で行う。

### 食品・環境

固定栄養は`data/<namespace>/data_maps/item/nutrition.json`で1個当たりのenergy_joules、protein_kg、fat_kg、water_kg、定性的なvitamin_groupsを持つ。個別の`ashen_frontier:nutrition`を固定値より優先し、未定義値を栄養あり/無害と補わない。`crop_species`は既存保存種子/菌類の種別IDで、栽培や遺伝を計算しない。

`FoodIntake.from`は1個分の栄養・腐敗・数値汚染・放射能を読み取るだけで、消費・満腹度・生理更新はしない。実際の摂取は#112/M3がサーバーで一度だけ行う。

`EnvironmentSample`の温度K・圧力Pa・相対湿度0〜1はclimateが提供する。降水kg/m²と日射J/m²はstartTick〜endTick区間の積算、ticksPerDayは区間の日長で、日長変更時は区間を分ける。降水時は水質IDも必要。覆い/換気は局所の状態で、安全/疾病判定ではない。生産コードに固定環境や既定提供者を持たず、固定値はGameTestだけで使う。

### 表示と検証

`CommonRecipe.displayLines`をJEI/EMIで共有し、時計・個数/保持・水質/kg・工具摩耗・損失・容器出力を英日で表示する。種別も既存自然物のツールチップに表示する。精密測定を解放するものではない。

GameTestで容器往復/異品質/0 kg、研究/設備/環境/個数、同時操作、満杯、取消、保存復元、reload変更、全出力、工具保持/摩耗、属性継承、Codec/同期と参照不正を検査する。時計換算は単体テスト、新規モジュール配線はagricultureのGameTest。GUIの視覚確認項目だけをpublish.mdに残し、この作業でクライアントは起動しない。

## #107の実装上の取り決め（2026-11-24）

確定済みの打製・繊維・木工をprimitiveで実装する。自然配置と初期配布の登録はcoreの既存IDを使用し、#59の配置は変更しない。弓錐専用部材、火起こし具・火口・炉・土器は#108以降とし、Bでは追加しない。

### 原料・操作と保存

- 礫を持ってShift右クリックすると1個を打製作業面へ置く。配置判定は既存BlockItemの経路を使う。作業面は素手で破壊・回収でき、保管した原料・工具・出力も落とす。
- 礫1個から石の打撃具を所持品で単純組立する。打撃具の既存登録ID・1 kgの質量は変えない。
- 台石は右クリックで原料・工具を実際に所持品から移す。材料のShift投入はまとめて行う。空手で上面をShift右クリックすると製法を切り替え、側面では保管物を回収する。空手の通常操作で開始・出力回収、作業中のShift操作で取消。
- 木の柄と掘り棒の製法を別々に選べる。剥片による切削に加え、研究済みの両面加工石器でも切削できる。繊維布の編み枠は同じ作業面の繊維作業として扱い、独立した設備IDは増やさない。

## #108の実装上の取り決め（2026-11-25）

確定済みの摩擦着火・成形・乾燥・焼成をprimitiveへ追加する。ろ過・煮沸と水源は#109・#55、自然配置は#59、環境の提供と室内の熱・排煙の評価はM3が担当する。M3が未接続の製品では、環境依存の工程を停止して未接続と表示する。固定環境の提供者はGameTestの中だけに置く。

### 製法・質量と操作

- 弓錐は柄・枝・紐・礫を既存の2×2単純組立で作る。乾燥した部材だけを受け付ける。質量2.9 kg、非スタック、摩耗上限64。乾燥繊維1 kgを台石で10実秒ほぐし、火口10個（各0.1 kg）にする。湿った繊維から乾いた火口へ迂回できない。
- 石囲い炉は礫2個と粘土玉1個で3 kg、乾燥棚は枝2個と紐2個で2.2 kg。両設備とも非スタックで、設置は既存BlockItem、操作はサーバーで行う。
- 成形には台石の入力4スロットと4 kgの槽を使う。粘土玉2個（各1 kg）・砂1個（0.5 kg）・原水または清浄水0.5 kgを10実秒で、生の土器1個（3 kg）にする。粘土玉・砂は既存のバニラ自然素材を用い、代替の同等IDを増やさない。水は既存WaterTankの容器移送だけを使い、世界の水源・帯水層には接続しない。
- 台石は密封水容器または土鍋から通常操作で1 kg、Shift操作で最大4 kgを受け取る。土鍋のShift操作では槽から容量4 kgまで回収する。水質の混合を拒否し、容器の残量・槽は共通のmg格子で同時に変更する。密封水容器の容量を独断で定義せず、空容器への補充は追加しない。
- 生・乾燥土器は非スタックの同一ID群を使い、成分 `ashen_frontier:pottery_form` のpot/lid/tubeで形状を区別する。乾燥棚の覆い・換気・気温273.15 K超・相対湿度0.8以下を満たす区間で、1ゲーム日（GAME時計86,400秒）乾燥する。自由水0.5 kgを損失として記録し、乾燥品は2.5 kgとなる。
- 焼成は炉内973〜1123 Kで120実秒（REAL時計）、加工への供給熱量2.1 MJを必要とする。乾燥品2.5 kgから土鍋1個（2.5 kg）、または蓋・陶管5個（各0.5 kg）を得る。蓋・陶管も成形から同じ工程を経る。土鍋は非スタック、空のCONTENT_MASS 0 kg、容量4 kg。数値汚染等は共通の継承規則で保持する。
- 炉・棚は原料を右クリックで1個、Shiftでまとめて投入する。空手の通常操作で開始・再開・出力回収、Shift上面で製法選択、稼働中のShiftで取消、Shift側面で保管物回収、Shift下面で取消・消火する。取消・出力満杯では入力を消費しない。所持品に入らない回収物は既存の所持品追加・ドロップ経路で残りを落とす。
- 着火は乾いた火口・燃料・摩耗しきっていない乾いた弓錐・覆い・換気を必要とする。主手の同じ弓錐を保持し、4 m以内で30実秒操作する。成功時だけ火口1個と摩耗1を消費する。持ち替え・離脱・環境不足は中断し、再操作で再開する。明示取消では着火時間を0に戻す。この蓄積時間は操作を圧縮するゲーム上の扱いである。
- `ashen_frontier:moisture_kg` は追加の自由水kgを示す。乾いた素材・部材・火口・弓錐には0を初期値として付け、既存の成分Ingredientで乾燥条件を照合する。木材に含まれる平衡含水分まで0とする意味ではなく、M3の天候を仮定する値でもない。

### 熱・時間・保存の境界

炉は既存FuelDataとMaterialDataを使い、乾いた枝のdry_wood profileを受け付ける。FAOの気乾木材（含水率10〜20%）の代表値16 MJ/kgを採用する。乾いた枝1 kgを16 MJの残存化学エネルギーへ移して保持し、実際に燃やした分だけ減らす。燃料切れは停止とし、乾燥品を無作為に破壊しない。

炉の熱モデルは待ち時間を圧縮するゲーム値として、燃焼出力120 kW、炉体への配分5%、加工への配分最大15%、有効熱容量500 J/K、放熱時定数7200ゲーム秒（参照日長で5 W/K相当）、炉内上限1123 Kとする。適温区間の実際の燃焼時間だけを焼成へ加える。熱・時間の両条件を満たすまで出力を確定しない。土器類の比熱1000 J/(kg·K)、2.1 MJ/バッチも代表化したゲーム値であり、考古学的な炉の測定値から直接導出したものではない。化学発熱量を超えて熱を生成しない。

炉は20tick、棚は200tickごとのscheduled tickで、前回のgameTimeから遅延評価する。毎tickのBlockEntity tickerは設けない。1回の処理は一定個数のスロットと1スタック（最大64個）の燃料だけを扱う。稼働炉100台ならおよそ100回/実秒、棚100台なら10回/実秒の評価となる。隣接チャンク探索・室内探索・外部ケイパビリティは追加しない。

入力・出力・加工進捗はProcessingStation、未燃焼燃料・火口・残存燃料エネルギー・余熱・着火時間は設備が所有する。炉・棚の破壊では全状態を標準BLOCK_ENTITY_DATAに保存した設備アイテム1個だけを落とし、再配置で戻す。水入りの台石も同様に1個へ保存し、通常lootとの二重回収を避ける。水なし台石は従来どおり内容物を個別に落とす。保存・チャンク復元・再配置では作業者を復元せず再操作待ちとし、未ロード時間を加工・燃焼へ加算しない。プレイヤーなしのBlockEntity復元を可能にする。

B時点の台石保存は1入力・容量1 mgを保持している。未リリース形式への移行処理は加えず、この保存をそのまま読む。Cの成形には内容を空にして通常回収・再設置した新しい台石を使う。ID・CONTENT_MASSのkg double形式は変更しない。

### 共有API・研究・表示

- `core/environment/EnvironmentQuery`: サーバースレッドで同期発火するNeoForge Event。位置と開始・終了gameTime tickの区間に対し、M3がEnvironmentSampleのSI単位・覆い・換気・日長を提供する。samplesは連続した区間列を返し、sampleは瞬時/単一区間だけに用いる。応答区間列が要求の開始・終了と一致せず、欠落・重複・ゼロ長の挿入があればIllegalArgumentException。未応答はOptional.emptyで、設備は進行せず再操作待ちとなる。区間中に条件・日長が変わる場合は、その境界で評価を分ける必要がある。
- `core/environment/CombustionEvent`: 実際に評価した区間、燃料profile、燃焼質量kg、化学発熱量J、設備へ留保した熱Jを通知する。留保熱は炉体蓄熱の増減と実際に加工へ供給した熱の和。冷却だけの区間では質量・化学発熱量0、留保熱は負となる。M3が差分の放出熱とprofile別の排煙を扱い、M4がCO濃度や安全な室内を仮定しない。
- `ProcessingStation`の温度付きstart/advance/finishは、外気温と別の炉内温度Kを受け取る。advanceのavailableSecondsは型のREAL/GAME時計での適合区間秒数の上限で、実経過を超えて加算しない。負・非有限の値は拒否する。finishは炉内温度を出力の既存温度成分へ刻み、入力・槽・出力を従来どおり一括確定する。
- `CommonRecipe.serverDisplayLines(ServerPlayer)`はサーバー側の研究状態とSI表記で条件を表示し、クライアント設定へアクセスしない。JEI/EMIは従来のCommonRecipe表示を再利用する。正確な炉の実測温度計は追加せず、設備の状態表示は冷たい・適温等に留める。
- 初回の弓錐・火口・炉・棚・基本土器成形・乾燥を研究でロックしない。摩擦着火の成功がt0/fireを解放して基本土鍋の焼成へ進み、土鍋の完成がt0/potteryを解放して蓋・陶管へ進む。所持・拾得だけで製造実績にしない。
- バニラの炉・燻製器・溶鉱炉・焚き火2種・火打石と打ち金・ファイヤーチャージを既存recipe_disabledタグへ追加し、着火・加熱の迂回を止める。バニラ以外の共有タグや一般燃料互換は追加しない。

## #108反証後の修正（2026-11-25）

追加自由水moisture_kgはアイテム1個あたりのkgとする。登録をcoreのNaturePropertiesへ移し、ID `ashen_frontier:moisture_kg` と保存・通信のdouble形式を維持する。ProcessingStationの共有継承だけで、全消費原料の個数分の自由水を合算し、全出力のMaterialData質量へ比例配分する。属性の継承先指定に含まれない原料の湿りも失わない。各出力は1個あたりの自由水を持つ。未消費・保持原料の自由水は動かさない。固体の加工損失を蒸発とみなさず、追加自由水の総量を製品へ残す。湿りのある原料を継承する製品は質量データを必要とする。単純組立のinheritは原料1個分の自由水を出力個数へ等分する。製法別の湿潤拒否例外では前段加工の問題を解決しない。

## 炉の冷却規則の確定（ユーザー承認: 2026-11-25）

炉の余熱は**常にGAME時計で冷える**。チャンクが未ロードの間も含め、保存したlastTickから次の評価時刻までをM3のEnvironmentSampleの日長でゲーム秒へ換算する。dayTimeの変更は使わない。加工・摩擦着火・燃料消費・焼成のREAL時計、および未ロード中は加工・燃焼を進めない取り決めは維持する。

冷却は既存ItemPropertyMath.coolを使い、T(g)=Ta+(T0−Ta)exp(−g/7200)とする。TaはM3が当該区間に提供した気温K、gは経過ゲーム秒。時定数7200ゲーム秒、有効熱容量500 J/Kは炉の形状を省略するゲーム値であり実測値ではない。参照日長24000tickでは7200ゲーム秒が100実秒に相当し、従来の5 W/K・500 J/Kの冷え方を保つために選んだ。日長が変わったときの冷却は、その日長で換算したGAME秒に従う。

燃焼中も放熱は同じGAME時計で計算する。燃焼出力・炉体への5%・加工への最大15%はREAL時計による発熱量とし、燃焼した区間に対する一定入熱と指数放熱を同時に積分する。燃料切れ後の残り区間は入熱0で冷却する。炉内温度上限1123 Kは燃焼時の上限であり、無燃焼の冷却だけに人工的な温度上限を当てない。焼成は973〜1123 K・120実秒・供給熱2.1 MJのままとする。

lastTickは温度状態に対応する評価済みgameTime tickで、設備の保存へlast_tickとして含める。作業区間用のworkTickとは分け、再開時に冷却時刻を現在時刻へ置き換えない。操作時、次のwork、チャンク読込み後の1回のscheduled tickで、保留していた冷却をまとめて評価する。アイドル状態の毎tick/継続tickerは加えない。設備アイテムへの回収・再配置でも保存した冷却時刻を維持する。

M3の区間入力がなければ、仮の気温で冷却せずlastTickも進めない。後から必要区間を覆う入力が得られたときに評価する。日長・気象が変化する区間の分割は既存のEnvironmentSample契約に従う。固定の環境を配布実装へ追加しない。

無燃焼の冷却通知では、燃焼質量・化学発熱量・加工供給熱は0、留保熱はC(T後−T前) Jとなる。冷却なら負となり、M3が放出熱として受け取る。評価済み時刻を更新し、同時刻の再操作・再保存で放熱を二重通知しない。保存復元の評価にプレイヤーを要求しない。

未リリースの炉保存へlast_tickを追加した。冷却時刻を持たない従来の開発用炉・設備アイテムは作り直し、旧形式の移行処理は追加しない。登録IDやCONTENT_MASSの保存形式は変えない。

回帰GameTestは、ロード中の放置、未評価のロード期間を保存した後の未ロード期間、標準のBlockEntity保存/復元とonLoad、日長24000/12000、dayTime変更の無関係、環境未接続と再接続、放熱通知・同時刻再評価を検査する。未ロード期間はBEを取り外し、実チャンク保存と同じsaveWithFullMetadata→loadStatic→onLoadの経路で復元して検証する。さらに構造物から512ブロック離れた専用チャンクを保存し、強制ロードを外して実アンロードを確認後、ディスクから別のBEへ再読込みする試験を行う。試験後に専用の強制ロード・環境入力を解除し、時刻を戻す。単体試験でもGAME秒だけの指数冷却と燃料・加工を進めないことを検査する。

M3の実環境は#132/#133/#134/#135、室内は#137、涵養は#136。単一EnvironmentQueryで複数の日長/天候区間を平均化せず、#132で区間列と炉/棚の呼出し元を改修する。既存APIの説明と実装の改修完了は区別する。

## #132：環境区間列と日長履歴

EnvironmentQuery.samples(level, position, from, to)はOptional<List<EnvironmentSample>>。provide(List)は要求範囲と正確に一致する順序付き区間列を検証し、不変コピーを保持する。正の要求にゼロ長区間は挿入しない。瞬時照会は積算0の1件。単一sampleは複数区間を平均化せずemptyを返す。提供者なしの既定環境は追加しない。

ProcessingStation.advanceIntervalは評価済み時刻に連続する小区間だけを進め、欠落/再送/未来区間ではfalseで進捗を変更しない。不適合時間もavailableSeconds=0として時計だけ区間末尾へ進める。炉/棚のworkが区間順に処理する。未ロードの作業は再開時に時計を合わせて加算せず、余熱のcoolToだけが未評価全区間をGAME冷却する。

DayLengthHistoryは単調tick上の日長変更と保存用changesスナップショットを持つ純粋計算。GameTime.gameSeconds(from,to,history)とTimeBasis.seconds(from,to,history)でGAMEだけを区間積算する。履歴の保存/設定変更の記録を担う本番providerは#133以降で接続し、#132では配布用固定値を設けない。

### #132反証後の修正：製品の温度評価時刻

区間列の途中で完成する製品は、finishへ渡したEnvironmentSample.endTickを温度の記録時刻にする。環境を使わない即時加工は現在時刻。温度の5 K丸めは維持するが、確定時刻を20tick境界へ丸めない。以降のcurrentTemperatureはこの完成時点から冷却する。遅延更新でも元の記録時刻より前へ丸めず、完成前への逆向き評価を避ける。保存/通信の形式は変更しない。
