# アーキテクチャ（確定）

## M3の確定範囲（2026-11-25）

M3 Q1〜Q8は全て推奨案で承認済み。[14](14-m3-climate-survival.md)を詳細正本とする。M3はA「気候とM4接続」、B「生理・感染」、C「序盤動物」に分割し、Aのみで全体完了としない。

高度な星空/惑星描画・建築被害・精密観測器・重症医療/ワクチン・家畜治療/細胞採取等の移管先は[15](15-phase1-followups.md)。従来の確定目標は維持し、M3の実装時期についてはこの決定を優先する。

既存貯留の蒸発・減水・水位の共有契約は未決定。[#136](https://github.com/rs0325/ashen-frontier/issues/136)と水量正本の[#122](https://github.com/rs0325/ashen-frontier/issues/122)/実配置の[#123](https://github.com/rs0325/ashen-frontier/issues/123)で調整する。非負補給APIへの負量入力や残量の二重保存は行わない。


ビルド構成は[../development.md](../development.md)を参照。ここではMod単位の責務と、全モジュール共通の仕組みを定める。

## モジュール構成

機能Modは文明段階（Tier）ではなく技術ドメインで分ける。1つのTierは複数のドメインにまたがり（例: 蒸気文明＝金属加工＋熱・圧力＋回転動力）、ドメイン単位のほうが依存関係が安定するため。

| モジュール | 責務 | 主な依存 | 時期 |
|---|---|---|---|
| core | 共通API、ワールド生成で配置される全ブロック・アイテムの登録、バニラ要素の削除、データコンポーネント、単位系、研究基盤、個人端末基盤、チーム、設定、互換性チェック、救済コマンド、JEI・EMI連携 | — | 第1期 |
| world | 固定マップ生成、地域・バイオーム、地下構造・旧文明の構造物配置、初期シェルター、土壌、ワールド端の霧 | core | 第1期 |
| climate | 季節、気候・気象シミュレーション、水循環（降水・地下水）、室内の空気、空の描画 | core, world | 第1期 |
| survival | 生理パラメータ、負傷・疾病、睡眠 | core, climate | 第1期 |
| fauna | 家畜・野生動物・感染動物・海洋生物・旧文明のアンドロイド兵 | core, survival | 第1期（一部） |
| primitive | Tier 0の手作業（石器、火、簡易な浄水・調理、手動加工） | core | 第1期 |
| agriculture | 農業・土壌改良・交配・食品加工 | core, primitive, climate（環境入力） | 第1期 |
| kinetics | 回転動力（水車、風車、軸、歯車、動力消費機械） | core | 第1期 |
| metallurgy | 製錬・鋳造・鍛造・合金 | core, kinetics | 第1期 |
| steam | ボイラー、圧力容器、蒸気機関、工作機械 | core, kinetics, metallurgy | 第1期 |
| logistics | シュート・コンベア・仕分け機（後に空気輸送など） | core, kinetics | 第1期 |
| armory | 武器（銃・弾薬）・防具 | core, metallurgy | 第1期（Tier 0〜2） |
| vehicles | 自転車、手押し車、蒸気車両、鉄道（後に自動車・航空機） | core, kinetics, steam | 第1期（一部） |
| electrical / chemistry / electronics / nuclear / aerospace など | Tier 3以降 | 未定 | 第2期以降 |

- coreが大きくなりすぎないよう、coreは「登録と共通基盤」に限り、機械・レシピ・振る舞いは機能Modに置く。
- 機能Mod間の依存は、ビルドの規約プラグインに依存先の指定を追加して表す（現状はcoreへの依存だけ自動）。依存は循環させない。

## ワールド生成コンテンツの安定性

固定マップには、第1期の時点で全Tierの旧文明の痕跡（宇宙港、原子力発電所など）が配置される。そのため次を規約とする。

1. ワールド生成で配置されるブロック・アイテムは、機能が未実装でもcoreで先に登録する（例: 「損傷した蒸気タービン」は第1期には分解・回収だけでき、修理による再稼働は後のモジュールで実装する）。
2. 後から機能を付けるときは、登録IDを変えずに、ブロックエンティティの振る舞い・データコンポーネント・レシピを追加する。
3. マップの構成（地形・地域・主要構造物の位置）は**マップ版**として管理する。生成済みチャンクは更新されないため、マップ版を上げる変更（主要構造物の追加・移動）は新規ワールドだけに反映されることを明記して提案する。未生成チャンクだけに追加できる小規模な追加は互換の範囲とする。

## 共通基盤（core）

| 仕組み | 内容 |
|---|---|
| 単位系 | 内部はSI単位。表示用の変換・書式化を共通化する |
| データコンポーネント | 摩耗、温度、組成・純度、腐敗、栄養などアイテムの性質（[06](06-items-and-physics.md)） |
| 材料データ | 硬度・密度・比熱・融点などをデータマップ（データパック）で定義し、アイテム種別に結び付ける |
| レシピ基盤 | 温度・圧力・時間・エネルギー・触媒などの条件を持つ共通レシピ形式。JEI・EMIの表示はcoreで一括して行い、各モジュールはレシピ型を登録するだけにする |
| 研究基盤 | 観測・実験・製造実績・資料の条件を持つデータ駆動の研究ツリー（[07](07-progression.md)） |
| 個人端末 | ロストしないUI。拡張モジュールで表示できる情報が増える（[05](05-player.md)） |
| チーム | 研究進捗の共有単位。他Modに依存しない最小限の仕組み |
| 互換性チェック | 許可リスト外のModを検出して警告する |
| 救済 | 詰み回避用のコマンド・設定 |

## 他Modとの関係

- **許可リスト【確定】:** JEI、EMI、Sodium、Iris。OptiFineはNeoForge 1.21.1向けの版が確認できないため対象にせず、描画最適化はSodium・Irisで代替する。外部の情報表示Mod（ミニマップ、Jadeなど）は許可リストの対象外とする。Ashen Frontier内蔵のミニマップ・全体マップは個人端末とは別に誰でも使える（2026-11-22決定、Issue #80）。
- **警告の出し方【確定】:** タイトル画面とワールド参加時に1度表示し、ログにも記録する。起動は止めない。サーバー側でも検出し、参加者へ通知する。
- **共有しないための規約:** 共通タグへの登録をしない。エネルギー・アイテム・流体のケイパビリティは自Mod内部の独自のものを使い、外部から抜き差しできないようにする。

## 性能

- 毎tickの処理を避ける。生理は1秒ごと、気象セルは10〜30秒ごと、季節・地下水は数分ごとを目安にする。
- 動力・流体・蒸気ネットワークは、構成が変わったときに再解析し、定常状態では計算を省く。
- 腐敗・冷却などの時間変化は、タイムスタンプから必要時に計算する（インベントリを毎tick更新しない）。
- 描画負荷の大きい演出（砂嵐の粒子、雲、遠景の気象）は品質設定で段階的に削れるようにする。
- 目標: 4人程度のマルチプレイで、Modによるサーバー負荷の増加をバニラ比で小さく保つ。具体的な予算は第1期の計測で決める。

## マルチプレイ

- 処理はサーバー権威。クライアントには表示に必要な値だけを同期する（生理は本人だけ、気象は周辺セルだけ）。
- 研究はチーム単位で共有、生理・端末は個人単位。
- 初期シェルターの必須物資は、プレイヤーごとに配布する（先着で取り尽くされないようにする）。
